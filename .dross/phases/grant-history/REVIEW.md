## FLAG
- [antipatterns / test design] The reused-id guard `started_at >= child.created_at` (header, t-6) compares timestamps from two different clocks, and the existing test fixtures will trip over it. `children.created_at` is always wall-clock `time.Now().Unix()` (internal/store/children.go:143, no injection). Grants take the caller's or engine's clock, and the existing harnesses pin that clock in the past: the store tests use `t0 = 2026-09-21` (internal/store/grants_test.go:12), the API harness uses `t0 = 2026-09-20` (internal/api/login_test.go:36), and `seedGrant` in cmd/adguard-reward/main_test.go:780 starts grants an hour before the child it just created. On those fixtures every grant is filtered out. That means t-6 `TestListGrantHistory_Paging`, `_RemovalsAndExtensions` and `_Legacy`, and t-9 `TestHistory_NameSnapshotEndToEnd`, `_ExtendedAndTrimmed` and `_Paging`, will all see empty histories. Meanwhile `_ReusedChildID` passes without testing anything, because every grant is filtered whether or not it belongs to the reused id. The reverse also fails: with real-clock grants, timestamps are whole Unix seconds, so a test that deletes a child and recreates it in the same second gets `started_at == created_at`, and `>=` leaks the old child's history. That makes the reused-id test flaky instead of vacuous. Either way, the executor will have to make an unplanned design decision partway through t-6.
  Suggestion: decide in the plan how `created_at` is controlled in tests. Options include seeding `children.created_at` by SQL in the history tests, or letting CreateChild take a time. Make `TestListGrantHistory_ReusedChildID` set both timestamps explicitly, including the case where they fall in the same second. Also state whether the boundary is `>=` or `>`, and accept that same-second reuse is ambiguous.

- [test contract specificity] No contract checks that a trimmed service keeps its snapshot name. The locked `service_names` decision says the snapshot is "shown forever after", and c-3 says a removed service is still listed on its grant. t-6 `_RemovalsAndExtensions` asserts only `removed_at` and reason. t-9 `_ExtendedAndTrimmed` asserts only `removed_reason`. Suppose ListGrantHistory joins names through the live `grant_services` rows. Trim deletes those rows, so the removed service would drop to the live-catalogue or bare-id fallback, and every current contract would still pass.
  Suggestion: extend t-6 `_RemovalsAndExtensions` (or t-9 `_ExtendedAndTrimmed`) to assert that the trimmed service comes back with its snapshot name. Include a grant that was ended by its last trim.

## NOTE
- [granularity] t-4 bundles three separate behaviours: end_reason derivation, the extension log with the `ExtendGrant` signature change, and name snapshots with the `CreateGrantNamed`/`CreateNamed` interface switch. All of them go in the same four files, so splitting would only serialise tasks on those files and gain no parallelism. Leaving it as one task is defensible. Expect this to be the largest diff in the phase.
- [locked decision: service_names] t-9 `TestHistory_CatalogueDown` accepts bare ids for unsnapshotted services while AdGuard is down. That would also apply to a pre-upgrade grant whose custom service still exists. Custom names live in the local store (CustomServiceStore), so the handler could still show the "current name" the locked decision requires without AdGuard. This is degraded-mode behaviour that the decision doesn't address, so it is not a conflict. It may be worth resolving custom ids from the store even when the AdGuard catalogue fails.
- [test contract specificity] t-6 has no store-level contract for an unknown or deleted child (the sentinel ListGrantHistory returns). This is covered end-to-end only by t-9 `TestHistory_Errors`, which uses the real store in the API harness, so it is caught, but only one layer up.
- [strengths] The header pins the schema, the wire shape (field names, `[]`-never-null, status enum, cursor semantics) and the 404/400/401 matrix. That lets the web chain (t-2 → t-5 → t-8) run in parallel with the backend chain without drifting, and t-9 `TestHistory_GoldenKeys` enforces the shape.
- [strengths] The locked `legacy_end_reason` decision is guarded at three independent layers: t-1 (no backfill, byte-identical legacy rows), t-9 `TestEndStatus` (`(ended, NULL)` → `ended_unknown`, never `ended_early`) and t-5 (the "Ended (reason unknown)" label).
- [strengths] The contracts anticipate real hazards in the existing code. App.svelte's `refresh()` calls `navigate($route)`, which would drop `?child=` on reload (t-8). End and expiry record a reason only after AdGuard confirms the revert (t-4, t-10). Keeping DELETE-on-trim means trimmed services still free the (child, service) slot and custom-service deletion (t-3 `TrimFreesService`). SQLite reuses child ids (t-6).

## Summary
Coverage is complete, the waves are ordered correctly and no task conflicts with a locked decision or a rule. The plan can proceed once the `created_at` clock mismatch is resolved, because it will otherwise empty or destabilise the t-6 and t-9 history tests.
