## FLAG
- [test-contract] t-2's lockout formula `lockedUntil = now + BaseLockout << (trips-1) capped at MaxLockout, trips++` overflows once the cap is sticky. `trips` keeps incrementing on every trip even after the lockout is pinned at 1h, and `1m << 28` exceeds `math.MaxInt64` (1m = 6e10 ns; 6e10 x 2^28 ~ 1.6e19 > 9.2e18). In Go a signed left shift wraps silently, so at trip #29 the computed duration goes negative (or, at shift >= 53, to exactly 0), `min(d, MaxLockout)` picks the wrapped value, `lockedUntil` lands in the past, and the IP is unlocked. An attacker who retries as soon as each 1h lockout ends reaches trip #29 in ~29 hours and the "capped at 1h" guarantee in c-11 stops holding. No contract exercises more than 8 trips, so a literal implementation passes every test. The same line is also ambiguous about whether `trips` is read before or after the increment: read-before with `trips = 0` gives a shift count of -1, which panics at runtime.
  Suggestion: state the order explicitly (`trips++; shift := min(trips-1, 6); lockedUntil = now + min(BaseLockout<<shift, MaxLockout)`), or stop incrementing `trips` once the lockout equals MaxLockout, and add to `TestPerIP_Doubling`: "trip #40 still yields exactly 1h".

- [test-contract] t-4 `TestAuthenticate_Garbage` asserts "raw with one flipped character -> ErrNoSession". A 43-character `base64.RawURLEncoding` token carries 258 bits for 256 bits of payload, so the last character has two unused low bits. Go's non-strict decoder ignores them: flipping the final character from e.g. `A` to `B` (or `Q`, `g`, `w`) decodes to the same 32 bytes, the same SHA-256, and the session is accepted. Depending on which character the test picks the contract is either green or red for reasons unrelated to tamper-resistance, and the malleability itself means two distinct strings name one session.
  Suggestion: decode with `base64.RawURLEncoding.Strict()` and reject anything that is not exactly 32 decoded bytes; pin the flipped index in the contract (e.g. "character 10") or flip a character in the first 42.

- [test-contract] t-9 `TestLogin_Burst` (12 concurrent wrong-password posts, `Hang` 30ms -> exactly 5 fake hits, 7 x 429) depends on `Limiter.Fail(ip)` being recorded *before* the in-flight slot is released. The description orders "Check again while holding it; then call AdGuard.Login; ErrBadCredentials -> Fail" but never says the slot is held through Fail. An executor who releases the slot as soon as AdGuard answers (to shorten the critical section) lets the next queued request pass its second Check with the counter still at 4, producing a 6th hit and a flaky test.
  Suggestion: add "the slot is released only after Fail/Issue has run (defer the release for the whole critical section)" to the description.

- [antipattern] t-5 `TestNoStore` asserts on "a 404 for an unknown route" via `API.mux`. t-9 then mounts a `"/api/v1/"` catch-all -> `RequireSession(NotFound)`, after which any unmounted `/api/v1/*` path without a cookie answers 401, not 404. If the t-5 test asserts the status (not only the header) it goes red when t-9 lands, and t-9's `files` does not include `internal/api/middleware_test.go`.
  Suggestion: in t-5, have `TestNoStore` assert only `Cache-Control` on that case (or drive the 404 through a path the catch-all cannot claim), or add `internal/api/middleware_test.go` to t-9's `files` with a note that the 404 case becomes a 401.

- [granularity] t-3 still touches 6 files across two packages (`internal/config` x4 and `internal/api` x2) whose halves are independent: `api.ClientIP` takes parsed nets and never imports `config`. First pass suggested a split and the author kept it as one task; that is a legitimate call, but it remains the wave-1 task with the most surface (9 contracts, two test files, an example-config test) and the two halves will land as one commit.
  Suggestion: keep as is if the executor commits it as one unit deliberately; otherwise split into config-key and resolver tasks, both wave 1.

- [granularity] t-7 mixes the fetch layer with test tooling (vitest devDependency, `vite.config.ts` test block, `pnpm-lock.yaml`, three Makefile targets). The amended description now states the `pnpm install` / node_modules consequence, which was the first-pass ask, so this is a residual observation: the only contract guarding the tooling half is "the Makefile test target's prerequisites include test-web".
  Suggestion: acceptable; the executor should run `make test` end to end (not just `pnpm test`) before committing so the new prerequisite chain is observed green.
