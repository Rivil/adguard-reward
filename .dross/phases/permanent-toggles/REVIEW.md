# Plan Review — permanent-toggles

Reviewed: 2026-11-03
Plan: 12 tasks across 4 waves

## BLOCKING
- [locked-decision: revert_baseline_v2] t-5 says revert must go through the new `applyPlan`, and `applyPlan` treats a `use_global` client as failed ("use_global -> failed (global list never written)", which TestApplyPlan pins). That is fine for Toggle and Reconcile. It changes revert's behaviour, though. Today `revert` (`internal/grants/grants.go:285-318`) doesn't read clients at all: it calls `AddBlockedServices` on every stored client, and that writes the per-client list with only a warning (`internal/adguard/clients.go:226`). A grant can legitimately cover a global-list client. `Create` stores the grant with that client and returns Failed=[Kid tablet] (TestEngine_CreateFailedClients "global list"). Under t-5, that grant's revert always reports the client as failed, so `expireLocked` leaves it active with no timer. The reconciler then retries it every tick, and it never expires until a parent migrates the device. Meanwhile `grant_services_live_idx` turns every new grant for that (child, service) into `*ErrGrantOverlap`. This also conflicts with the locked revert_baseline_v2, under which revert still re-blocks every covered client (set-union) except permanently-open ones. Under t-5, a `use_global` client is neither re-blocked nor let through. No test guards against this: no existing test expires a grant that covers a global-list client.
  Suggestion: keep revert's current per-client behaviour, i.e. write the per-client list and don't fail on `use_global` (an option or mode on `applyPlan`, or revert keeps its own loop over `dropOpen(revertPlan(...))`). Add a t-5 contract: a grant on a still-global Kid tablet expires to status expired and leaves youtube in its per-client list.

## FLAG
- [antipattern: file-scope] t-12 has to make `Toggle` call `syncRules` for `custom:<n>` ids, but `Toggle` lives in `internal/grants/toggle.go`, which belongs to t-8 and isn't in t-12's files (`toggle_custom.go`, `toggle_custom_test.go` only). t-8 can't call a function that only t-12 defines without breaking its own build. So a writer held to t-12's file list can't wire the region write in, and TestToggle_CustomUnblock can't pass.
  Suggestion: add `internal/grants/toggle.go` to t-12's files, or have t-8's description name the dispatch point (e.g. t-8 ends custom ids at a `toggleCustom` stub in toggle.go, and t-12 replaces its body).

- [test-contract: 5 s budget] t-11 says "a request deadline bounds the catalogue read so catalogue + Toggle fit in 5 s". However, `applyContext` (`grants.go:476`) builds Toggle's 4 s budget from `context.WithoutCancel(ctx)`, so the request deadline doesn't shorten it. That leaves about 1 s for the catalogue read plus the wait for `e.mu`, and a Reconcile pass can hold `e.mu` for its own full 4 s ApplyTimeout. The contracts don't cover any of this. TestToggle_CatalogueSlow only checks the 502 path for a 10 s hang. Nothing tests a catalogue that succeeds slowly (say 1.5 s) followed by an engine that runs its full 4 s, or a Toggle queued behind a running Reconcile. t-12 also adds an `EditUserRules` GET+POST to the custom path, and no deadline contract covers that.
  Suggestion: say how long the catalogue deadline is, and add a t-11 contract with a slow-but-successful catalogue plus a hanging `/control/clients/update` that asserts the response comes back in under 5 s. Say whether waiting on the mutex counts toward the budget. Add a deadline case to t-12.

- [locked-decision wording: shared_client_scope] The locked decision says "The toggle response names the shared devices it affected". t-11 builds `shared` from `sharedOf(child.Clients, ...)` (`internal/api/grants.go:69`), which lists every shared client the child has, whether or not the toggle touched it. In TestToggle_BlockSharedHeldOpen (t-8), A blocks youtube and B's permanent unblock keeps tv open, so tv is deliberately left alone. Yet t-11's TestToggle_SharedReport would still report tv as shared and affected, and t-10 shows a notice naming tv and B. Under the "affected" reading, that tells the parent the block reached a device it didn't reach.
  Suggestion: decide which reading is meant. If "affected" means "the intent applies to it", leave it and note that in the wire header. If it means "written", filter `shared` to the clients the plan actually wrote and add a held-open case to TestToggle_SharedReport.

- [test-contract] t-4's `controlFor` contract defines the result by state (blocked -> ['unblock'], partial -> both) and by toggle ('unblocked' -> ['block']) separately. It never says which wins when the two disagree, and both combinations are reachable. After an applied=false unblock, the row reads `{state:'blocked', toggle:'unblocked'}` until the reconciler converges. Offering ['block'] there hides the retry. When a co-owner keeps every one of A's clients open, A gets `{state:'unblocked', toggle:'blocked'}`.
  Suggestion: add both combinations to toggles.test 'controlFor' with explicit expected arrays.

- [test-contract] t-9's TestReconcile_ToggleReadFailure expects the "grant half and region half still run" after a `ListServiceToggles` error. But t-5 makes `syncRules` read toggles fail-closed (TestSyncRules_ToggleReadFailure: 0 set_rules POSTs), so the region half aborts on the same error. A test written to t-9's wording, asserting the region converged, would fail against t-5's code.
  Suggestion: reword it to "grant half still runs; region half writes nothing (fail-closed, t-5); 0 toggle writes".

- [locked-decision (prior phase)] t-9 changes `baselineFrom` so it drops services an owner unblocked and adds the child's permanent blocks. That amends auto-client-labelling's locked `new_client_blocked_set` (siblings' effective set + the child's active-grant services). This spec explicitly supersedes phase 04's `revert_baseline` with `revert_baseline_v2`, but records no supersession for `new_client_blocked_set`.
  Suggestion: either record the amendment in the spec as a superseding decision, or justify it in t-9 as following from drift_enforcement (the reconciler would converge the new device on its next tick anyway).

- [test-contract] TestCreateClient_BaselineToggles (t-9) has no active grant in it. Today `baselineFrom` adds the child's active-grant services after it has built the sibling union (`clients.go:181-188`). So an implementation that drops the permanently-unblocked services before that step adds youtube back whenever the child also has a live youtube grant. The contract misses that ordering bug. The next reconcile tick would undo it, but the device starts out blocked.
  Suggestion: add one case with youtube both under an active grant and permanently unblocked, where the new client must still exclude youtube.

## NOTE
- [coverage] All five criteria are covered: c-1 by t-4/t-8/t-9/t-10/t-11/t-12, c-2 by t-1/t-4/t-7/t-8/t-9/t-10/t-11/t-12, c-3 by t-2/t-5/t-8, c-4 by t-1/t-5/t-9, c-5 by t-3/t-4/t-6/t-10. Every `depends_on` points to an earlier wave and no task could move up a wave. There are no rule violations. Built-ins are validated against the live catalogue (r-01), and custom toggles reach AdGuard only through `syncRules` -> `EditUserRules` under `e.mu` (r-02). `DeleteService` and `Toggle` share `e.mu`, and custom ids are AUTOINCREMENT, so t-8's existence check can't race a delete or match a reused id.
- [round-1 follow-through] The round-1 findings were fixed: `revertPlan` is unchanged and `dropOpen` is applied around it; the toggle type is local to grants; t-5 owns one apply helper; t-8 now spells out how the trimmed grant's off-owner clients are written; TestToggle_CatalogueSlow was added; and the custom path was split out into t-12.
- [parallelism] t-8 and t-9 both run in wave 3 in package `grants`, and both will want a "seed a toggle" or "child with clients" helper in their `_test.go` files. If both writers define one under the same name, the second commit won't compile. t-5 (wave 2) could own a shared helper, or each writer could prefix its helpers.
- [wording] t-12's "(or a block that trims a custom service from a grant)" says nothing extra. A custom service is only trimmed by a block on that `custom:<n>` id, which the first clause already covers.
- [strength] The wire-conventions header pins the store, engine, HTTP and view shapes and the open-wins precedence. That is what lets four wave-1 tasks across store, grants, blocked and web run in parallel without guessing at each other's types.
- [strength] The contracts are written as failure cases with exact fixtures and POST counts, and they consistently test fail-closed reads (TestRevert_ToggleReadFailure, TestSyncRules_ToggleReadFailure, TestReconcile_ToggleReadFailure). Missing that case is what would unblock every child.
- [strength] Dependencies are kept tight: t-2 leaves `revertPlan`'s signature alone so the existing `TestRevertPlan_*` cases still pass unmodified, t-9 seeds toggles through the store so it doesn't need t-8, and t-1 includes `custom_services_test.go` because of its "0007 last" migration-order assertion.

## Summary
Coverage is complete and the cross-task seams are mostly pinned, but routing revert through `applyPlan` with "use_global -> failed" means a grant on a global-list device can never expire. That must be fixed before execution, and t-12's file scope needs `toggle.go` to wire in the custom region write.
