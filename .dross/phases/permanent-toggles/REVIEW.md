# Plan Review — permanent-toggles

Reviewed: 2026-11-03
Plan: 12 tasks across 4 waves

## BLOCKING
- [locked-decision: new_client_blocked_set_v2] Under the v2 baseline, a co-owner's permanent unblock leaks onto a child's new device, and nothing ever re-blocks it. Today `baselineFrom` (`internal/grants/clients.go:151-189`) adds the services of "any active grant (of any child) stored on a known sibling" back into the baseline. That clause exists because the sibling's effective list is open for another child's reason. TestBaseline_SharedSiblingGrant pins it: Ada's grant on the shared Kid phone must not leave Ben's new tv open. A permanent unblock is the same situation, but v2 has no matching clause. Example: Kid phone is shared by Ada and Ben, Ada permanently unblocks youtube, and Ben gets a new tv. The sibling union is Kid phone's list, which no longer contains youtube. Ben owns no unblock to subtract. So the tv is created with youtube open. v2's `why` ("drift_enforcement would converge the device on its next reconcile tick anyway") doesn't hold here. Ben has no toggle row for youtube, so t-2's togglePlan classifies it as "AdGuard-owned (no write)", and the tv stays open for good. Separately, v2's wording ("∪ every service under the child's active grants") drops the existing other-child-grant-on-sibling clause. A t-9 writer who follows the locked text literally will break TestBaseline_SharedSiblingGrant. t-9's description repeats the same ambiguous wording ("active-grant services").
  Suggestion: amend v2 before t-9 runs. Restate the existing sibling-grant clause. Add the permanent analogue: services that an owner of a known sibling has permanently unblocked, where that owner does not own the new client, join the union before the final subtraction. Add a t-9 contract with the Ada/Ben/Kid phone/tv fixture above, asserting that Ben's tv blocks youtube.

## FLAG
- [locked-decision: toggle_partial_apply] A failed block write to a trimmed grant's unmapped client is stranded, but the locked decision promises "the reconciler converges them". t-8 runs SetServiceToggle first: t-1 deletes the `grant_services` row in the same tx. Only then does it applyPlan over mapped clients ∪ the pre-trim grant's stored clients, so that old-tablet (unmapped) gets re-blocked. If that one write fails, nothing retries it. The grant no longer lists youtube, so neither revert nor the grant half of Reconcile touches it. t-9's toggle half only plans for current owners' clients, and old-tablet has none. Today a failed revert leaves the grant active and the reconciler retries it (`expireLocked`, `grants.go:352-376`). The trim removes that safety net. TestToggle_BlockOldDevice only covers the success path.
  Suggestion: either record this in t-8 as an accepted limitation, alongside the use_global one, or say how the failed unmapped client stays reachable for convergence. Then add a TestToggle_BlockOldDevice failure case that pins whichever behaviour is chosen.

- [test-contract / seam] `ToggleResult.Clients` is never defined for custom ids, yet t-11 builds the `shared` report from it. t-8 defines Clients only for the built-in write paths and hands custom ids to t-12 ("their region write is t-12"). t-12 specifies Applied and Failed for custom ids but not Clients. All t-11's shared-report contracts (TestToggle_SharedReport, TestToggle_SharedHeldOpen) use youtube. So a custom unblock that reaches a shared tv could return `shared: []`, or a custom block held open by a co-owner's @@ cover could name tv, and no test would catch it. That is the misreport the round-2 finding about "affected" devices was meant to close.
  Suggestion: make t-12 define Clients for custom ids under the same rule as t-8: exclude a client held open by another owner's unblock or a live grant cover. Add a custom case to TestToggle_CustomUnblock, or to one of the t-11 shared tests.

- [test-contract] The built-in unblock path in t-8 skips `applyPlan` ("Remove on every mapped client"), so its handling of use_global clients and missing clients is left unpinned. `RemoveBlockedServices` on a use_global client writes the per-client list and only logs a warning (`internal/adguard/clients.go:225`). A literal implementation would therefore report Applied=true while AdGuard's global list keeps the device blocked. That contradicts t-8's own "use_global client -> in Failed" limitation, and the parent sees a success that didn't happen. TestToggle_PartialApply's use_global case and its "clients read 502 -> 0 update POSTs" case don't say whether they block or unblock. The description also never says the unblock path reads clients first, which the 502 case requires.
  Suggestion: state in t-8 that unblock reads clients and classifies them the way applyPlan does (gone -> skipped, use_global -> Failed). Split TestToggle_PartialApply's use_global and 502 cases into explicit block and unblock variants.

## NOTE
- [coverage] All five criteria are covered: c-1 by t-4/t-8/t-9/t-10/t-11/t-12, c-2 by t-1/t-4/t-7/t-8/t-9/t-10/t-11/t-12, c-3 by t-2/t-5/t-8, c-4 by t-1/t-5/t-9, c-5 by t-3/t-4/t-6/t-10. Every `depends_on` points to an earlier wave, and no task can move up a wave. t-12 shares `toggle.go` with t-8, so it has to follow it. No rule is violated: built-ins are checked against the live catalogue (r-01), and custom toggles reach AdGuard only through `syncRules` under `e.mu` (r-02). The interfaces that gain methods (grants.Store, api.ChildStore, api.Grants) are only faked in tests by structs that embed the interface (`rename_test.go:181,187`, `children_test.go:707`, `grants_test.go:740`), so adding methods won't break any fake.
- [round-2 follow-through] Every round-2 finding was addressed. revert keeps its own loop with use_global as warn-only, and TestExpire_GlobalClient guards it. t-12 now owns `toggle.go`. The 1 s catalogue / 4 s apply split is stated, mutex wait is explicitly outside the budget, and TestToggle_SlowCatalogueThenHang and TestToggle_CustomDeadline were added. `shared` is filtered through Clients. Both controlFor disagreement cases are pinned. t-9's read-failure contract now matches t-5's fail-closed region. v2 was recorded in the spec, and the grant+unblock ordering case was added.
- [spec reading] c-2 says "every mapped client of the child is blocked". shared_client_scope (open-wins) means a shared client held open by a co-owner's unblock or live grant stays open, and TestToggle_BlockSharedHeldOpen asserts exactly that. /dross-verify should read c-2 through the locked decision instead of failing it on a held-open tv.
- [helper duplication] t-5 adds a `childWithClients` test helper to grants_test.go, but `env.child(name, clients...)` already exists in the same package (`internal/grants/clients_test.go:21`) and is used throughout. A second helper with the same job adds noise. Reusing `env.child` is enough.
- [scope] t-8's block path runs "togglePlan for the child's mapped clients" without restricting it to the requested service. So one block also converges drift on other toggled services on those clients. That is harmless and arguably correct, but it makes POST-count assertions such as TestToggle_Idempotent depend on fixtures having no other drifted toggles.
- [UI staleness] t-10 refetches only the toggling child's blocked view. If a co-owner's disclosure is open on the same page, it keeps showing the old unblocked-by attribution until it is reopened.
- [strength] The contracts target the seams that actually fail: fail-closed reads on revert, region and reconcile; the unblock subtraction ordered after the grant union (TestCreateClient_BaselineGrantAndUnblock); and the custom-id existence check racing DeleteService. Each one names a fixture and an exact POST count.
- [strength] The wire-conventions header plus t-2's pure planner (togglePlan/dropOpen/permanentOpen with `revertPlan` left unchanged) let the store, grants, blocked and web layers build in parallel in wave 1. The existing TestRevertPlan_* cases still act as a regression gate.

## Summary
The plan is sound and closes every round-2 finding. The v2 baseline it implements, though, lets a co-owner's permanent unblock open another child's new device permanently, and the locked decision needs amending before t-9 runs. The three flags are contract gaps at the trim, custom-shared and unblock-use_global seams.
