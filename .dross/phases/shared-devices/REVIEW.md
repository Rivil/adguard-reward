# Plan Review — shared-devices

Reviewed: 2026-11-02
Plan: 17 tasks across 3 waves

## BLOCKING
- [wave-order / files] t-1 (wave 1) removes the client check from the store's `checkConflicts`. That check is the only thing that turns POST /api/v1/children with a taken client into a 409: `handleChildCreate` (internal/api/children.go:143) calls `CreateChild` directly, and the API-side `updateConflict` pre-check runs only on PUT. The existing `TestChildren_Conflicts` (internal/api/children_test.go:165-169) asserts that POST `{Cy, [Kid phone]}` returns 409 naming Ada and that the store is unchanged. Once t-1 lands, POST returns 201 and that test fails. Its file belongs to t-8, which is in wave 2. So t-1 cannot reach a green `make test` inside its declared files, and wave 1 ends red. With commit-gating, that means either a red commit or an edit outside the task's scope.
  Suggestion: give t-1 ownership of the POST client-taken case in TestChildren_Conflicts (add internal/api/children_test.go to its files, or move TestChildren_CreateShared into t-1). The other option is to state explicitly that t-1's gate is scoped to `./internal/store/...` and that the full suite is expected to stay red until t-8.

## FLAG
- [test-contract] t-8 drops the client check from `updateConflict`, but none of its contracts or its description mention `TestChildren_PutAtomic` (internal/api/children_test.go:183). That test proves PUT is atomic by using the client-ownership 409 as its only failure trigger: Ada PUT with Ben's "Old laptop". After t-8 the PUT returns 200, so the test fails. A quick fix that just flips the expectation would also delete the only "no half-applied PUT" guard.
  Suggestion: name TestChildren_PutAtomic in t-8. Have it keep the atomicity assertion but switch to a conflict that still exists, such as a name-taken PUT that also changes clients.
- [locked-decision] `shared_device_rule` (locked) says a service is re-blocked only when "no active grant (of any owner)" still covers it. The plan reads this through each grant's *stored* clients (plan header, t-2 `TestRevertPlan_StoredClients`, t-5 `TestExpire_ClientUnassigned`). In practice, a grant from a child who has since been removed from the device, or deleted, keeps that service open on it. That child is no longer an owner. This does not contradict the locked decision outright, because it matches the earlier locked client_set ("grant stores the clients it unblocked at creation"). But it does settle an ambiguity in a locked decision without any spec decision recording that choice.
  Suggestion: confirm with the user that "owner" means "owner when the grant was created", and record that in the spec before execution.
- [antipattern] t-5 owns reconcile.go but does not address `Stats.Writes`. Its doc says it "counts the Add/Remove calls", and the overdue branch does `st.Writes += len(g.Clients)` (reconcile.go:62). With ref-counted revert, a client that another grant fully covers gets no AdGuard call (t-5's own `TestEngine_CoveredNoWrite`), so Writes will overcount on that path.
  Suggestion: either have revert report how many writes it actually made and make Reconcile count those, or loosen the Stats doc. Then add a single assertion to `TestReconcile_OverdueSharedKeepsOther` on whichever behaviour is chosen.
