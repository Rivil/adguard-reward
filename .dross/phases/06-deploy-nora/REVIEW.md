## FLAG
- [antipattern / test hygiene] t-4's `TestBuildLinux` runs the real `make build-linux`, whose prerequisite is `build-web` (`pnpm build`, which empties `web/dist` before refilling it). Under `go test -race ./...` packages compile and run concurrently, so a package whose test binary embeds `//go:embed all:dist` (e.g. `web`) can be compiling while cmd's TestBuildLinux is emptying `dist` — a build-time race that will show up as an intermittent embed error or a test binary with missing assets. It also runs vite twice per `make test`.
  Suggestion: have the test drive the go-build step without the web prerequisite — e.g. `make build-linux` with the `build-web` prerequisite overridable (`WEB_DEPS=` / a `build-linux-bin` sub-target the -n recipe test still covers) — so the test never touches `web/dist`. Keep `TestMakeBuildLinuxRecipe` asserting the `build-linux: build-web` chain textually.

- [test contract / precondition] t-5's first contract asserts "./data was not created". `cmd/adguard-reward/data/adguard-reward.db` already exists on this machine (gitignored, dated 2026-09-21), so a plain existence check is order- and machine-dependent: it passes vacuously in a clean checkout and fails or lies where the dir pre-exists. Since `run()` is in-process, `os.Chdir` to a temp dir is not safe for parallel tests in the package.
  Suggestion: assert the negative on the db file's absence or unchanged mtime/size inside `./data` captured before `run()` starts, or (cleaner) assert that `store.Open` was pointed at `<STATE_DIRECTORY>` via the "listening"/startup log line and the db file inside it, and drop the "./data was not created" clause.

- [rules / secret handling] t-7 says "on nora write the AdGuard password into the 0600 credential file (`umask 077; cat > ...`)". It does not say who does it. If the executing agent does this over `ssh`, the password would have to pass through the conversation or argv, which the global secret-handling rules forbid (no secrets in argv, secrets move file-to-file). The step is fine only as a human action on nora's terminal.
  Suggestion: make the task text explicit that the credential write is performed by the user on nora (or via an interactive `! ssh nora` step), and that the agent only re-runs `make deploy-nora` afterwards and confirms exit 0. The r-03 contract (grep -q boolean) already covers the recording side.

- [antipattern / files] t-7's `files` is `.dross/phases/06-deploy-nora/verify.toml`, but that file is generated by `dross verify` (`generated_at`, `finalized`, per-criterion `notes` — see phase 04/05). Phase 05 recorded its manual install-prompt observation inside verify's `notes` during the verify workflow, not by hand-editing the file in the execute step. A hand-written verify.toml in t-7 risks being overwritten when verify runs, or colliding with its schema.
  Suggestion: keep the locked decision (records land in verify.toml) but state the mechanism: t-7 captures the observations (date, device, timings, versions) in the task's commit body / a notes input that `dross verify` carries into `[[criterion]].notes` for c-4/c-5/c-7. Also record device model/OS this time — phase 05's finding notes that was omitted.

- [granularity] t-6 is the heaviest task: a ~100-line bash installer with first-run guard, edit-preservation, health polling, version gate, journal dump, tailscale serve, secret hygiene; plus a Makefile target and nine test contracts across two test surfaces (script stubs and `make -n` chain). Three files, but the script alone is several distinct behaviours.
  Suggestion: consider splitting the Makefile `deploy-nora` chain + `TestMakeDeployNoraChain` + `TestInstallPathMatchesUnit` into a small follow-on task in the same wave, leaving t-6 as "the script and its stub tests". Not required if pair-mode executes it in one sitting.
